## 内存逃逸

面试题: Golang内存逃逸现象是什么?

1. 什么是逃逸?

   逃逸是指在函数内部创建的对象或变量, 在函数结束后仍然被其他部分引用或持有 (脱离了函数的作用域)

   

2. 对内存管理的理解

+ 栈上内存的分配和释放由编译器自动管理, 速度快但是空间有限
+ 堆上分配的内存需要运行时系统的参与, 相对较慢但是空间较大, 由GC回收



3. 逃逸带来的影响

+ 分配和回收的开销增加 (在栈上面, 函数执行完成之后, 所对应的局部变量都是立马回收了, 如果逃逸到堆上, 那就必须由GC回收, 增加了回收的开销)
+ 指针引用和内存安全 (在函数内部的局部变量, 都是在函数内的作用域内, 不用担心有其他协程会访问到这个局部变量, 但是如果这个对象或变量逃逸之后, 那么其他的协程就可能访问到了, 所以存在内存安全问题)
+ 内存泄漏风险 (如果GC回收不及时, 或者回收出现了问题, 就会导致内存不断增加, 增加内存泄漏风险)



4. 识别逃逸场景,规避不必要的内存逃逸

+ 并不是所有的逃逸都不被允许, 只是说有些不必要的逃逸需要规避. 同时可以合理的去利用内存逃逸, 比如说闭包函数, 就是对内存逃逸的合理利用



5. 导致内存逃逸的原因是什么?

+ 栈空间: 栈空间是否足够, 比如说大变量 导致栈空间无法容纳, 就会逃逸到堆上; 
+ 返回局部变量指针: 函数结束后,指针被其他变量所引用
+ 编译时无法确定类型或大小: 比如说interface{}或多态实现, 比如定义了一个interface{}类型的变量不赋值, 编译器就不确定他是什么类型. 那么这个变量就会在堆上分配. 

+ 闭包引用外部变量: 变量被闭包持有, 生命周期延长
+ 变量被 goroutine 使用: goroutine 生命周期不可控



6. 根本原因?

​	和golang内存分配的基本原则有关:

+ 栈上面的对象的指针不能被存储到堆中
+ 栈上面的对象的指针的生命周期不能超过这个栈对象的生命周期. 也就是说这个对象回收了,对应指针一定要被回收, 如果说指针不能被回收, 那就挪到堆上面去



7. 查看逃逸分析结果

```
go build -gcflags="-m" main.go
```



8. 逃逸分析是编译期还是运行期？

+ Golang 的逃逸分析是在编译期完成的。
   编译器会在编译阶段分析变量的生命周期和作用域，判断变量是分配在栈上还是堆上。
   如果变量可能被函数外部引用，就会发生逃逸分配到堆上。
   这样可以避免运行期判断带来的性能开销。
   需要注意的是，具体的内存分配是在运行期执行的，但分配策略在编译期已经确定。



9. 为什么有时候明明看起来不会逃逸，结果还是逃了？

+ 有时候变量看起来不会逃逸但实际上发生逃逸，是因为 Go 的逃逸分析采用的是保守策略。
   编译器只有在能够确定变量不会被外部引用时才会分配到栈上，否则就会分配到堆上。
   在 interface、函数调用、闭包、goroutine 等复杂场景下，编译器很难完全分析变量的生命周期，因此会倾向于让变量逃逸。
   本质上这是在性能和安全之间做的权衡，Go 选择了安全优先。



10. 如何减少逃逸?

+ 减少逃逸的核心是让变量的生命周期尽量局限在函数内部，让编译器能够确定它不会被外部引用。
   常见方法包括：避免返回局部变量指针、减少 interface 使用、避免不必要的闭包、goroutine 中使用值传递、控制对象大小等。
   可以通过 `go build -gcflags="-m"` 查看逃逸分析结果。
   但需要注意的是，减少逃逸不是绝对目标，需要在性能和代码可维护性之间做权衡。

## websocket和sse区别

WebSocket 和 SSE 都是用来做实时通信的技术。
 WebSocket 是全双工通信，客户端和服务端可以互相发送数据，适合聊天、游戏等高实时交互场景。
 SSE 是单向通信，只能由服务端向客户端推送数据，基于 HTTP 实现，适合消息推送、实时日志等场景。
 相比来说，WebSocket 功能更强但实现复杂，SSE 更简单且支持自动重连。实际选择要看是否需要双向通信。
