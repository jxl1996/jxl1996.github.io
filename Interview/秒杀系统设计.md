## 秒杀系统设计

golang面试题: 秒杀系统如何实现的，秒杀系统接口、流程设计、防止超卖?

### 秒杀系统的设计原则 

+ 秒杀系统的核心挑战是**瞬时高并发**。我的设计原则是：**尽量将请求拦截在下游之前**。通过‘层层过滤’，只让极少数有效的请求到达数据库。
+ **热点隔离：** 根据项目规模, 条件允许的情况下, 可以将秒杀业务与普通业务隔离（独立数据库、独立 Redis 实例、独立域名）

### 流程设计 (层层过滤)

**A. 客户端与接入层 (前端)**

+ **资源静态化：** 商品详情页使用 CDN 缓存。

+ **按钮置灰：** 提交后立即禁用按钮，防止用户连点。

**B. 秒杀前（预热阶段）**

+ 商品库存提前加载到 Redis

**C. 过滤层 (Golang 实现)**

+ **限流 (Rate Limiting)：** 使用 Golang 标准库的 `golang.org/x/time/rate`（令牌桶）或分布式限流（Redis + Lua）,或 Nginx 限流, 👉 防止请求直接打爆服务

**D. Redis 预减库存（核心）**

+ 所有的库存扣减必须在 **Redis** 中完成，不能直接请求 MySQL

**F. 异步下单**

+ 扣减成功后，通过 **消息队列 (RabbitMQ/Kafka)** 异步通知下游创建订单。👉 避免数据库被瞬间打爆

### 防止超卖

+ 第一层：Redis 原子扣减
  + 利用 Redis 的单线程原子性，使用 `DECR` 命令。我会将库存预先同步到 Redis 中。请求进来先执行 `DECR`，如果返回值小于 0，直接返回‘已售罄’。

+ 第二层：Lua 脚本 (保证原子性)
  + 为了防止‘查询库存 -> 判断 -> 扣减’这几步操作非原子化，我会使用 **Lua 脚本**。将逻辑封装在脚本中发送给 Redis 执行，保证判断和扣减是一气呵成的。

+ 第三层：数据库兜底 (乐观锁)
  + 在最后异步写库阶段，为了防止万一，MySQL 更新语句要带上条件约束：” `UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0;`

### Golang 接口实现细节

+ **使用 Context 控制超时：** 保证请求在链路过载时能及时释放资源。
+ **本地缓存 (FreeCache/BigCache)：** 进一步减轻 Redis 压力，缓存“活动是否结束”的状态。
+ **Channel 限制并发：** 在 Golang 内部利用 Channel 的 buffer 大小作为一道简单的“阀门”。

### 秒杀失败回滚

提问: 秒杀失败回滚怎么做？

秒杀回滚主要处理两种情况：一是**用户超时未支付**，二是**系统链路异常**（如扣减 Redis 成功但发 MQ 失败，或订单创建失败）。我们的目标是确保 Redis 中的库存最终能准确反映实际可售数量。

+ 场景一: 系统级异常（同步回滚）: 当 Redis 预扣成功，但后续逻辑（如入队 MQ）报错时，需要立即回滚。在 Golang 代码中，我会使用 defer 或者传统的 if err 判断。如果后续发消息失败，立即再次调用 Lua 脚本执行 INCRBY 将库存加回去。
+ 场景二：业务级异常（异步回滚/补偿）, 这是最常见的场景：用户抢到了，但没付钱，或者订单中心服务挂了。
  + A. 延迟队列清理: 订单创建时，同步发送一条“延迟消息”到 MQ，有效期通常为 15-30 分钟。延迟插件到期后，消费该消息判断订单状态, 如果是“待支付”或“已取消”, 调用 Lua 脚本把库存加回去
  + B. 分布式事务表 + 定时任务:  
    1. 在发送 MQ 前，先在本地数据库记录一条“扣减日志（状态：处理中）”。
    2. 定时任务轮询这张表，发现“处理中”状态超过一定时间的记录
    3. 去订单中心查询是否有对应订单
    4. 如果没有订单，说明链路断了，触发回滚逻辑（Redis +1），并更新日志状态。



提问: 如果你回滚多了怎么办？

+ **幂等性保证：** “回滚操作必须是幂等的。我会给每个秒杀请求生成一个全局唯一的 `RequestID`。在回滚 Redis 库存前，先去一个 `Rollback_Log`（通常也是 Redis 的 Set 或 Hash）里查一下这个 ID 是否已经处理过。只有没处理过，才执行 `INCRBY`。”

+ **库存上限校验：** “在执行回滚的 Lua 脚本里，可以加一个判断：`如果当前库存 + 回滚数量 > 初始总库存`，则报错，防止数据异常导致库存凭空增加。”
