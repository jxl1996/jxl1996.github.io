## Redis类型和使用场景

面试题: Redis类型以及各自的使用场景?

Redis 主要有 5 种基本数据类型，随着版本更新，还引入了位图（Bitmaps）、超日志（HyperLogLog）、地理位置（GEO）以及流（Stream）等高级类型。在实际开发中，可根据数据的结构化程度、访问频率和原子性要求来选择。

1. **String (字符串)**: String 是最基础的类型，可以存储文本、数字甚至是序列化后的对象

+ 使用场景：
  + **缓存：** 最常用的场景，存储 Session、Token 或简单的 JSON 对象。
  + **计数器：** 利用 `INCR` 和 `DECR` 命令实现原子自增，比如点赞数、播放量。
  + **分布式锁：** 利用 `SETNX` 指令（SET if Not eXists）来实现。

2. **Hash (哈希)**:  适合存储对象，特别是对象的字段经常需要单独更新时。相比 String 序列化整个对象，Hash 更加节省空间且灵活

+ 使用场景：
  + **用户信息/购物车：** 比如 Key 是用户 ID，Field 是商品 ID，Value 是商品数量。

3. **List (列表)**: List 是简单的字符串列表，按照插入顺序排序，底层实现是双向链表, 支持两端弹入弹出

+ 使用场景:
  + **消息队列：** 利用 `LPUSH` 和 `RPOP` 实现简单的生产消费者模型。
  + **最新动态：** 比如朋友圈动态、新闻列表，只保留最近的 N 条数据。

4. **Set (集合)**: Set 是无序且唯一的集合。它的核心优势在于支持**交集、并集、差集**运算

+ 使用场景：
  + **去重计数：** 比如记录 IP 访问量（UV）
  + **社交关系：** 利用交集实现“共同好友”，差集实现“可能认识的人”。

5. **ZSet (Sorted Set - 有序集合)**: ZSet 在 Set 的基础上增加了一个 Score 分数，数据按分数排序。

+ **使用场景：**

  - **排行榜：** 比如直播间实时贡献榜、热搜榜。

  - **带权重的任务队列：** 根据优先级处理任务。

6. **Bitmap (位图)：** 适合“只有两种状态”的极大数据量场景，如：**用户签到**、**日活统计**，非常节省内存。
7. **HyperLogLog：** 适合**基数统计**，比如统计网页的 UV(独立访客数）

8. **Geo 地理位置**: 

+ 场景:
  + **附近的人/店铺：** 比如微信附近的人、美团外卖搜索附近 3 公里的商家。
  + **距离显示：** 实时计算用户当前位置与目的地的距离。

## Redis对比Mysql原子性

面试题: Redis 和 MySQL 的原子性有什么区别？

它们虽然都叫‘原子性’，但在实现目标和结果上有本质不同。

+ **首先是回滚能力。** 	
  + MySQL 的原子性是**强一致性**的体现，它依赖 **Undo Log** 实现。如果事务执行一半失败，它能回滚到初始状态。
  + 而 Redis 的事务（MULTI/EXEC）**不支持回滚**，如果中间某条命令报错，它会继续执行后面的命令，只有 Lua 脚本能保证逻辑上的‘不被干扰’。

+ **其次是实现机制。** 
  + MySQL 是通过**锁机制和日志恢复**来在复杂的并发环境下模拟原子性。
  + 而 Redis 则是利用其**单线程模型**，天然地保证了命令执行的排他性，即在执行一个 Lua 脚本或事务队列时，其他请求必须排队。

+ **在实际应用中，**
  + 如果业务逻辑要求严格的‘要么全成功要么全失败’（如银行转账），我会选 MySQL。
  + 如果是为了应对高并发下的数据竞争，且逻辑简单（如秒杀扣减库存），我会利用 Redis 的 **Lua 脚本** 来利用其原子性特性。

## Redis原子性

Redis是怎么实现原子性的，可以回滚吗，为什么不设计一个回滚？

1. Redis 是如何实现原子性的？

  Redis 实现原子性主要依靠其**单线程模型**（这里指核心执行命令的线程）。

- **单条命令：** 由于 Redis 是单线程顺序执行，任何一条指令（如 `SET`、`INCR`）在执行期间都不会被其他指令插入。这种“排他性”保证了单条命令的原子性。
- **Lua 脚本：** Redis 将整个 Lua 脚本作为一个整体执行。在脚本运行期间，Redis 不会执行其他客户端的命令。这保证了复杂逻辑（如：查询 -> 判断 -> 变更）的**强原子性**。
- **事务（MULTI/EXEC）：** Redis 事务会将命令放入队列，在执行 `EXEC` 时，它会一次性、按顺序执行完队列里的所有命令。在执行期间，不会被其他客户端打断。



2. 可以回滚吗?

**Redis 事务并不支持传统意义上的回滚**。如果事务中某条命令在运行时出错，Redis 会跳过它并继续执行后续指令，已经成功的不会撤销。



3. 为什么不设计一个回滚？

**A. 性能开销**

+ MySQL 为了支持回滚，必须维护复杂的 **Undo Log**（回滚日志）。每次修改数据前，都要先记录原始数据。 Redis 的设计初衷是**极速**。如果引入回滚机制，会极大地增加内存开销和逻辑复杂度，违背了 Redis “轻量、高性能”的定位。

**B. 错误类型** 

+ Redis 官方认为，事务中的执行错误通常是由**编程错误**引起的：

  - 例如，你在代码里本该写 `SADD` 却写成了 `ZADD`。

  - 这类错误在生产环境中应该通过测试阶段发现，而不是靠数据库的回滚机制来“兜底”。

**C. 保持简洁**

+ 内部实现的简洁性使得 Redis 非常稳定且易于维护。不需要像传统数据库那样处理复杂的事务冲突、死锁检测和日志恢复。
