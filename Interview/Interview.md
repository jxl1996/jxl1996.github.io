## 内存逃逸

面试题: Golang内存逃逸现象是什么?

1. 什么是逃逸?

   逃逸是指在函数内部创建的对象或变量, 在函数结束后仍然被其他部分引用或持有 (脱离了函数的作用域)

   

2. 对内存管理的理解

+ 栈上内存的分配和释放由编译器自动管理, 速度快但是空间有限
+ 堆上分配的内存需要运行时系统的参与, 相对较慢但是空间较大, 由GC回收



3. 逃逸带来的影响

+ 分配和回收的开销增加 (在栈上面, 函数执行完成之后, 所对应的局部变量都是立马回收了, 如果逃逸到堆上, 那就必须由GC回收, 增加了回收的开销)
+ 指针引用和内存安全 (在函数内部的局部变量, 都是在函数内的作用域内, 不用担心有其他协程会访问到这个局部变量, 但是如果这个对象或变量逃逸之后, 那么其他的协程就可能访问到了, 所以存在内存安全问题)
+ 内存泄漏风险 (如果GC回收不及时, 或者回收出现了问题, 就会导致内存不断增加, 增加内存泄漏风险)



4. 识别逃逸场景,规避不必要的内存逃逸

+ 并不是所有的逃逸都不被允许, 只是说有些不必要的逃逸需要规避. 同时可以合理的去利用内存逃逸, 比如说闭包函数, 就是对内存逃逸的合理利用



5. 导致内存逃逸的原因是什么?

+ 栈空间: 栈空间是否足够, 比如说大变量 导致栈空间无法容纳, 就会逃逸到堆上; 
+ 返回局部变量指针: 函数结束后,指针被其他变量所引用
+ 编译时无法确定类型或大小: 比如说interface{}或多态实现, 比如定义了一个interface{}类型的变量不赋值, 编译器就不确定他是什么类型. 那么这个变量就会在堆上分配. 

+ 闭包引用外部变量: 变量被闭包持有, 生命周期延长
+ 变量被 goroutine 使用: goroutine 生命周期不可控



6. 根本原因?

​	和golang内存分配的基本原则有关:

+ 栈上面的对象的指针不能被存储到堆中
+ 栈上面的对象的指针的生命周期不能超过这个栈对象的生命周期. 也就是说这个对象回收了,对应指针一定要被回收, 如果说指针不能被回收, 那就挪到堆上面去



7. 查看逃逸分析结果

```
go build -gcflags="-m" main.go
```



8. 逃逸分析是编译期还是运行期？

+ Golang 的逃逸分析是在编译期完成的。
   编译器会在编译阶段分析变量的生命周期和作用域，判断变量是分配在栈上还是堆上。
   如果变量可能被函数外部引用，就会发生逃逸分配到堆上。
   这样可以避免运行期判断带来的性能开销。
   需要注意的是，具体的内存分配是在运行期执行的，但分配策略在编译期已经确定。



9. 为什么有时候明明看起来不会逃逸，结果还是逃了？

+ 有时候变量看起来不会逃逸但实际上发生逃逸，是因为 Go 的逃逸分析采用的是保守策略。
   编译器只有在能够确定变量不会被外部引用时才会分配到栈上，否则就会分配到堆上。
   在 interface、函数调用、闭包、goroutine 等复杂场景下，编译器很难完全分析变量的生命周期，因此会倾向于让变量逃逸。
   本质上这是在性能和安全之间做的权衡，Go 选择了安全优先。



10. 如何减少逃逸?

+ 减少逃逸的核心是让变量的生命周期尽量局限在函数内部，让编译器能够确定它不会被外部引用。
   常见方法包括：避免返回局部变量指针、减少 interface 使用、避免不必要的闭包、goroutine 中使用值传递、控制对象大小等。
   可以通过 `go build -gcflags="-m"` 查看逃逸分析结果。
   但需要注意的是，减少逃逸不是绝对目标，需要在性能和代码可维护性之间做权衡。

## websocket和sse区别

WebSocket 和 SSE 都是用来做实时通信的技术。
 WebSocket 是全双工通信，客户端和服务端可以互相发送数据，适合聊天、游戏等高实时交互场景。
 SSE 是单向通信，只能由服务端向客户端推送数据，基于 HTTP 实现，适合消息推送、实时日志等场景。
 相比来说，WebSocket 功能更强但实现复杂，SSE 更简单且支持自动重连。实际选择要看是否需要双向通信。

## Redis 自旋锁

redis自旋锁如何实现?

+ Redis 自旋锁本质就是：通过不断尝试获取分布式锁（SETNX），失败就循环重试，直到成功或超时。

核心流程:

+ 客户端通过 SET NX 尝试加锁，如果失败就进入循环不断重试，这个过程就是自旋。
   为了避免死锁，需要设置过期时间。
   为了避免误删别人的锁，释放锁时需要校验 value，一般通过 Lua 脚本实现原子删除。



Redis 分布式锁有哪些坑?

+ 锁过期导致并发问题（最经典）: 
  + 线程 A 获取锁（过期 5 秒 -> 业务执行 10 秒（锁过期）-> 线程 B 获取锁 -> A、B 同时执行（锁失效）. 
  + 解决方案: 合理设置过期时间并设置续期机制
+ 误删别人的锁（严重问题）
  + A 获取锁（value=uuid1）-> 锁过期 -> B 获取锁（value=uuid2）-> A 执行完，直接 DEL, 把 B 的锁删了
  + 正确做法：value 必须唯一（UUID）, 用 Lua 脚本原子校验删除, 设置续期机制

+ 非原子操作（SETNX + EXPIRE分开）
  + SETNX lock 1 -> EXPIRE lock 5 : 如果 SETNX 成功后程序挂了, EXPIRE 没执行, 就会造成死锁
  + 正确做法: SET lock value NX EX 5  一步完成（原子操作）



SETNX和SET NX区别:

+ SETNX 是 Redis 的旧命令，只能在 key 不存在时设置值，但不支持设置过期时间，因此需要额外调用 EXPIRE，这两个操作不是原子的，可能导致死锁问题。
   SET NX 是 SET 命令的扩展写法，支持 NX 和 EX 参数，可以在一条命令中同时完成加锁和设置过期时间，保证原子性。
   因此在实现分布式锁时，应该使用 SET NX EX，而不是 SETNX。
   同时还需要使用唯一 value 和 Lua 脚本来保证释放锁的安全性。

## defer的作用和底层原理

在 Go 语言中，`defer` 的作用是**延迟执行函数调用**，它会在当前函数**返回之前**按照**后进先出**的顺序执行。

常见用途有三类：

1. **资源释放**（比如 `file.Close()`、`mutex.Unlock()`）
2. **异常处理**（配合 `recover` 捕获 panic）
3. **日志或埋点收尾逻辑**

**执行时机：**

- `defer` 语句在**声明时就会计算参数**
- 但函数调用会在**return 之后、真正返回之前执行**

> `return` 其实是分两步：

1. 给返回值赋值
2. 执行 defer
3. 真正返回

所以 `defer` **可以修改具名返回值**



**底层原理：**

从实现上看，`defer` 本质是**在函数栈上维护一个 defer 链表（或栈）**：

- 每遇到一个 `defer`，会把当前函数和参数**封装成一个结构体**
- 挂到当前 goroutine 的调用栈上
- 函数返回时，**从后往前依次执行**



defer 一定会执行吗？（陷阱题）

+ 不一定，以下情况不会执行：

  + 调用了 os.Exit()（直接退出进程）

  + 程序被 kill -9

  + 发生致命错误（如 runtime 崩溃）

## TCP三次握手

1️⃣ TCP 三次握手的本质是：**建立连接并同步双方的初始序列号（Sequence Number）**，确保双方收发能力正常。

+ 第一次握手（SYN）: 客户端向服务端发送一个 **SYN 报文**, 
  + 表示：客户端请求建立连接，并告诉服务端自己的初始序列号
+ 第二次握手（SYN + ACK）: 服务端收到后，回复一个 **SYN + ACK 报文**
  + 表示: 同意建立连接, 确认收到了客户端的 SYN, 同时把自己的序列号发给客户端
+ 第三次握手（ACK）: 客户端再发送一个 **ACK 报文**
  + 客户端确认收到了服务端的 SYN, 至此连接建立成功

> [!NOTE]
>
> 三次握手的目的就是：双方确认“自己能发、对方能收”，并同步初始序列号。



2️⃣ 为什么是三次，不是两次？

回答: 如果只有两次握手，服务端无法确认客户端是否具备**接收能力**。

👉 举个经典场景：

- 客户端发了 SYN（第一次）
- 服务端回复 SYN+ACK（第二次）
- 如果客户端没有收到这个包

此时：

- 服务端以为连接建立了
- 客户端其实不知道

👉 会导致**半连接问题 / 资源浪费**

所以必须第三次握手，让服务端确认客户端收到了。



3️⃣ SYN 攻击是什么？

**回答：**

攻击者伪造大量 SYN 请求，但不完成第三次握手，导致服务端：

- 大量半连接（SYN_RECV）
- 占满连接队列（backlog）

👉 导致正常用户无法连接



4️⃣ 三次握手过程中可以携带数据吗？

**回答：**

- 理论上：**第三次握手可以携带数据**
- 实际上：大多数情况下不会这么做



> [!NOTE]
>
> 总结: TCP 三次握手通过 SYN 和 ACK 的交互，不仅建立连接，还完成了双方初始序列号的同步，并确认双方的收发能力；三次是最小可靠次数，既避免资源浪费，又保证连接可靠性

## goroutine泄漏

面试题: 什么情况下会导致goroutine泄漏?

> [!NOTE]
>
> 回答: 在 Go 语言中，goroutine 泄漏指的是 goroutine 已经没有实际业务意义，但由于阻塞或缺乏退出机制，**无法正常退出，长期占用系统资源**。
>
> 常见的泄漏场景主要有以下几种：
>
> 第一，**channel 使用不当**。比如从 channel 读数据但没有写入，或者向 channel 写数据但没有消费者，以及使用 `range` 遍历 channel 但没有关闭，都会导致 goroutine 一直阻塞。
>
> 第二，**阻塞操作没有退出机制**。例如 `select` 没有 default 或退出条件，或者 goroutine 一直卡在某个等待逻辑中。
>
> 第三，**缺少超时控制**。比如发起 HTTP、RPC、数据库请求时，没有设置 timeout 或 context，导致 goroutine 一直等待响应。
>
> 第四，**context 使用不规范**。创建了带取消的 context，但没有调用 cancel，导致依赖该 context 的 goroutine 无法退出。
>
> 第五，**无限创建 goroutine**。比如在循环中不断启动 goroutine，但没有并发控制或回收机制，最终造成资源耗尽。
>
> 第六，**后台任务没有生命周期管理**。比如启动了常驻 goroutine，但没有停止条件。
>
> **总结一句话：**
>
> goroutine 泄漏的本质是：**goroutine 被阻塞或无法感知退出信号，导致生命周期失控**。
