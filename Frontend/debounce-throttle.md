## 防抖和节流

### 1. 防抖（Debounce）

**核心逻辑：** 只要你一直操作，我就一直计时。只有当你**停止操作**并超过指定时间后，我才执行一次。

**适用场景：**

- **搜索框输入：** 等用户输入完最后一个字才发请求（避免每打一个字母都查库）。
- **窗口大小调整（Resize）：** 等用户拖拽完窗口，才重新计算布局。
- **表单验证：** 输完一串手机号后再校验，而不是输一位校一位。

### 2. 节流（Throttle）

**核心逻辑：** 无论你操作多快，我都会按照**固定的频率**（比如每秒一次）来执行。

**适用场景：**

- **滚动监听（Scroll）：** 比如计算页面滚动到哪了，或者判断是否触底（这种场景需要实时反馈，不能等停下来才算）。
- **抢购按钮（Click）：** 疯狂点击时，每 500ms 只响应一次，防止暴力操作。
- **游戏中的技能释放：** 狂按键盘，但技能受冷却时间（CD）限制，只能匀速发出。

### 3. 核心区别对比

| **特性**     | **防抖 (Debounce)**          | **节流 (Throttle)**                    |
| ------------ | ---------------------------- | -------------------------------------- |
| **主要目的** | 只有在最后一次动作后执行     | 按照固定频率执行                       |
| **重置逻辑** | 每次触发都会**重置**计时器   | 触发后进入冷却期，冷却期内忽略后续动作 |
| **执行次数** | 连续动作中只执行**最后一次** | 连续动作中按时间间隔**多次执行**       |
| **反馈感受** | 有明显的延迟感               | 相对平滑、有节奏感                     |

### 4. 代码示例 (简易版)

```js
// 防抖实现
function debounce(fn, delay) {
  let timer = null;
  return function() {
    clearTimeout(timer); // 只要进来就清掉上一次的，重新计时
    timer = setTimeout(() => {
      fn.apply(this, arguments);
    }, delay);
  };
}

// 节流实现
function throttle(fn, delay) {
  let canRun = true; // 状态锁
  return function() {
    if (!canRun) return; // 冷却中，直接弹回
    canRun = false;
    setTimeout(() => {
      fn.apply(this, arguments);
      canRun = true; // 冷却结束，开锁
    }, delay);
  };
}
```



### 5. 下拉刷新和触底加载更多

#### 5.1 下拉刷新 (Pull Down Refresh)

**建议方案：不需要防抖或节流，通常使用“状态锁”。**

- **原因：** 下拉刷新通常是由系统原生提供的交互（如 UniApp 的 `onPullDownRefresh`）。用户手动下拉并松手后，只会触发 **一次** 刷新事件。
- **实现逻辑：**
  - **状态锁：** 只要用户触发了刷新，立即将页面状态设为“加载中”，并显示加载动画。
  - **拦截重复：** 如果前一次刷新请求还没完成，用户再次强行下拉，代码逻辑应直接 `return`，避免重复请求数据导致覆盖。
- **代码要点：** 请求完成后务必调用 `uni.stopPullDownRefresh()` 停止系统的下拉动画。



#### 5.2 上拉加载更多 (Reach Bottom)

**建议方案：节流 (Throttle) 或 状态锁（更推荐）。**

- **原因：** 当页面滑动到底部附近时，`onReachBottom` 可能会在短时间内被高频触发多次（取决于用户的滑动惯性）。
- **实现逻辑：**
  - **节流：** 限制请求频率，例如 1 秒内只准发一次请求。
  - **状态锁（业务标配）：** 定义一个变量 `isLoading`。
    1. 触底事件触发 -> 检查 `isLoading` 是否为 `true`。
    2. 若为 `true`（表示上次数据还没回来），则直接跳过。
    3. 若为 `false`，则设为 `true` 并发请求，请求回来后再设为 `false`。
- **差异：** 节流是基于**时间**的，状态锁是基于**请求结果**的。在网络慢的情况下，状态锁比节流更能有效防止重复请求。



> [!TIP]
>
> **开发小贴士：** 在 UniApp 中，处理上拉加载最舒服的体验不是靠节流函数，而是将 `onReachBottomDistance`（触底提前量）设置得稍微大一些（如 150-200），然后配合一个严谨的 `isLoading` 状态锁。这样用户感知不到“加载中”，数据就默默地补全了。
