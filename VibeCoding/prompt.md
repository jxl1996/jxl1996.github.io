# 提示词

## 一、Codex全局提示词

### 1. 提交说明提示词

```
使用中文，根据当前 Git 实际改动生成提交说明。

要求：

1. 先分析本次代码改动的核心目的，不要只根据文件名、目录名或 diff 中的单个局部改动生成。

2. 使用 Conventional Commits 格式：
   <type>: <简短中文描述>

3. type 根据改动内容选择：
   - feat：新增功能
   - fix：修复问题
   - refactor：代码重构，不改变功能
   - perf：性能优化
   - docs：文档修改
   - style：代码格式调整，不影响逻辑
   - test：测试相关
   - chore：构建、依赖、配置或其他维护工作

4. 标题使用中文，简洁明确，尽量控制在 50 个字符以内。

5. 描述本次提交“做了什么”，不要使用“修改代码”“更新文件”“优化代码”等过于笼统或无意义的描述。

6. 如果包含多个相关改动，提炼最主要、最能代表本次提交目的的改动作为标题。

7. 如果多个改动彼此无关，仍优先根据本次提交最核心的改动生成一个标题，不要虚构不存在的统一目的。

8. 不要添加没有在实际 Git 改动中出现的内容，不要推测尚未实现的功能。

9. 如果改动明确属于某个模块，可使用：
   <type>(<scope>): <简短中文描述>
   如果 scope 不明确，则不要强行添加。

10. 只输出最终提交说明，不要解释分析过程，不要添加 Markdown、引号或其他额外内容。

示例：
feat: 新增用户登录接口
fix: 修复订单重复提交问题
refactor: 重构 RabbitMQ 消息消费逻辑
chore: 更新项目依赖
feat(auth): 新增短信验证码登录
```

### 2. 拉取请求提示词

```
使用中文，根据当前分支相对于目标分支的实际 Git 改动生成 Pull Request 标题和描述。

生成前应分析当前分支与目标分支之间的整体 Git diff 和提交记录，理解本次 PR 的核心目的，不要仅根据单个提交、文件名或局部代码改动生成。

PR 标题：

1. 简洁概括本次 PR 的核心目的。
2. 使用 Conventional Commits 风格：
   <type>: <简短中文描述>
3. type 根据主要改动内容选择：
   - feat：新增功能
   - fix：修复问题
   - refactor：代码重构，不改变功能
   - perf：性能优化
   - docs：文档修改
   - style：代码格式调整，不影响逻辑
   - test：测试相关
   - chore：构建、依赖、配置或其他维护工作
4. 标题使用中文，简洁明确，尽量控制在 50 个字符以内。
5. 不要简单罗列文件名、目录名或多个零散改动。
6. 如果包含多个相关改动，提炼最主要、最能代表本次 PR 目的的改动作为标题。

PR 描述按照以下结构生成：

## 改动说明

简要说明本次 PR 的核心目的，以及能够从实际改动中确认的必要背景。

## 主要改动

- 列出本次 PR 的主要功能或代码改动。
- 合并相似或关联的改动。
- 重点描述行为、业务逻辑、接口或实现方式的变化，而不是简单罗列文件。
- 不需要描述无关紧要的格式调整或机械性改动。

## 影响范围

说明本次修改实际涉及或可能影响的模块、接口、配置、数据库、依赖或现有功能。

如果从实际改动中没有发现明显影响，写：
- 无明显影响

## 测试情况

仅根据实际能够确认的信息说明测试情况。

如果能够从执行结果或上下文确认已执行测试，列出实际执行的测试或检查。

如果无法确认是否执行过测试，写：
- 未确认执行测试

不要推测或虚构测试结果。

其他要求：

1. 只根据当前分支与目标分支之间的实际 Git diff 和相关提交记录生成内容。
2. 不要编造不存在的功能、问题、背景、测试结果或影响范围。
3. 不要把 commit message 简单拼接成 PR 描述，应根据整体改动进行归纳。
4. 内容保持简洁，避免同一内容在多个章节重复描述。
5. 描述“做了什么”和产生了什么实际变化，避免使用“修改代码”“更新文件”“优化相关逻辑”等过于笼统的描述。
6. 小型改动可以缩短各章节内容，但保留基本结构。
7. 只输出最终 PR 标题和描述，不解释分析过程，不添加额外说明。
```

### 3. 全局指令

```
1. 编写代码时遵循当前语言、框架和项目的最佳实践，并优先遵循项目已有的代码风格和约定。
2. 合理规划代码、文件和目录结构，重视可读性、可维护性和可扩展性，避免不必要的过度设计。
3. 仅在必要时添加简洁的中文注释，重点解释业务逻辑、设计意图和不直观的实现，避免为简单代码添加无意义注释。
4. 使用 Go + GORM 定义数据库模型时，为表和字段添加 comment，保持数据库结构可读。
5. Go 业务代码原则上避免使用 panic，优先返回并处理 error；仅在程序无法继续运行的初始化阶段等必要场景使用。
6. 编写或修改代码后，尽可能使用对应语言或项目的格式化、Lint、类型检查或测试工具进行检查。
```
