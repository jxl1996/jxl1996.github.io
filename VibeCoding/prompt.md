# 提示词

## 一、Codex全局提示词

### 1. 提交说明提示词

```
使用中文，根据当前 Git 实际改动生成提交说明。

要求：
1. 先分析本次代码改动的核心目的，不要只根据文件名生成。
2. 使用 Conventional Commits 格式：
   <type>: <简短描述>

3. type 根据改动内容选择：
   - feat：新增功能
   - fix：修复问题
   - refactor：代码重构，不改变功能
   - perf：性能优化
   - docs：文档修改
   - style：代码格式调整
   - test：测试相关
   - chore：构建、依赖、配置或其他维护工作

4. 标题使用中文，简洁明确，尽量控制在 50 个字符以内。
5. 描述“做了什么”，不要使用“修改代码”“更新文件”等无意义描述。
6. 如果包含多个相关改动，提炼最主要的改动作为提交标题。
7. 不要添加没有在实际代码改动中出现的内容。
8. 只输出最终提交说明，不要解释生成过程。

示例：
feat: 新增用户登录接口
fix: 修复订单重复提交问题
refactor: 重构 RabbitMQ 消息消费逻辑
chore: 更新项目依赖
```

### 2. 拉取请求提示词

```
使用中文，根据当前分支相对于目标分支的实际 Git 改动生成 Pull Request 标题和描述。

要求：

PR 标题：
1. 简洁概括本次 PR 的核心目的。
2. 使用 Conventional Commits 风格：
   <type>: <简短描述>
3. 使用中文。
4. 不要罗列文件名。

PR 描述按照以下结构生成：

## 改动说明

简要说明本次 PR 的目的和背景。

## 主要改动

- 列出本次 PR 的主要功能或代码改动
- 合并相似改动
- 重点描述行为和逻辑变化，而不是简单罗列文件

## 影响范围

说明本次修改可能影响的模块、接口、配置、数据库或现有功能。
如果没有明显影响，可以写“无明显影响”。

## 测试情况

根据实际能够确认的信息说明测试情况。
不要虚构已经执行过的测试。

要求：
- 只根据实际 Git diff 和提交记录生成内容。
- 不要编造不存在的功能、问题、测试结果或影响。
- 内容保持简洁，避免重复描述。
- 小型改动可以适当精简章节。
- 只输出最终 PR 标题和描述，不解释生成过程。
```

### 3. 全局指令

```
1. 编写代码时遵循当前语言、框架和项目的最佳实践。
2. 合理规划代码、文件和目录结构，需要保证可读性、可维护性和可扩展性，避免过度设计。
3. 仅在必要时添加简洁的中文注释，重点解释业务逻辑、设计意图和不直观的实现，避免给简单代码添加无意义注释。
4. 使用 Go + GORM 定义数据库模型时，为表和字段添加 comment，保持数据库结构可读。
5. Go 业务代码原则上不要使用 panic，优先返回并处理 error；仅在程序无法继续运行的初始化阶段等必要场景使用。
6. 所有编写的代码保持符合对应语言的格式规范，编写后进行格式化。
```
